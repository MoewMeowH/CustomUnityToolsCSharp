# HB_Lint

규칙을 C# 어셈블리 어트리뷰트(`[assembly: ...]`)로 받는 범용 Roslyn 분석기. 규칙 파일 한 곳에 적으면 그 규칙 어셈블리를 참조하는 코드를 검사한다. 검사받는 코드에는 아무것도 붙이지 않는다.

- 검사 로직은 분석기 코드(`src/HBLint.Analyzers`), 구체 규칙 · 메시지 · 심각도는 어트리뷰트(`src/HBLint.Attributes`).
- Unity 전용이 아니다. 분석기 · 어트리뷰트 모두 netstandard2.0이고 UnityEngine을 참조하지 않는다. Unity에 기대는 규칙은 `Requires`로 범위를 정한다.
- 규칙을 additional file이 아니라 C# 소스로 받는다 (Unity에서 additional file이 분석기로 넘어가지 않는 경우가 있어서).

## 구조

```text
unity/com.hb.lint/            Unity 패키지 (UPM) — 어트리뷰트 · 생성기 코어 소스의 원본도 여기
  Analyzers/                  분석기 DLL (tools/Build-UnityPackage.ps1이 빌드해 넣음)
  Runtime/                    규칙 어트리뷰트 (asmdef HBLint.Attributes, 의존 없음)
  Editor/Generator/           생성기 코어 (asmdef HBLint.Generator, 의존 없음, C# 9)
  Editor/                     설정 · 설치 · 자동 생성 · 메뉴 · 규칙 편집 창
  Tests/Editor/               EditMode 시험
src/HBLint.Analyzers/         분석기 (netstandard2.0, Microsoft.CodeAnalysis.CSharp 4.3 — Unity 6.3+)
src/HBLint.Attributes/        unity/…/Runtime 소스를 링크해 컴파일 (NuGet · .NET용)
src/HBLint.Generator/         unity/…/Editor/Generator 소스를 링크해 컴파일
src/HBLint.Generator.Cli/     생성기 CLI hblint-gen (net10.0)
tests/                        dotnet test
tools/Build-UnityPackage.ps1  분석기를 Release로 빌드해 패키지 Analyzers/로 복사
rules.schema.json             rules.json 스키마 (생성물)
samples/rules.json            규칙 예시 (원본)

```

어트리뷰트 · 생성기 소스는 `unity/com.hb.lint/`에만 있다 (사본 없음). 분석기 코드를 바꿨으면 `tools/Build-UnityPackage.ps1`을 돌려 패키지 DLL을 갱신한다.

## rules.json → LintRules.g.cs

규칙의 유일한 원본은 `rules.json`이다. `LintRules.g.cs`는 생성물이라 직접 고치지 않는다.

```json
{
  "$schema": "../rules.schema.json",
  "rules": [
    {
      "id": "unity-null-operator",
      "kind": "BanNullOperator",
      "description": "설명 (생성물에 주석으로 들어감)",
      "type": "UnityEngine.Object",
      "message": "Unity 오브젝트는 '== null' 또는 'if (obj)'로 확인하세요.",
      "requires": ["UnityEngine.CoreModule"],
      "severity": "Warning"
    }
  ]
}
```

- `id`(필수, 영문 · 숫자 · `.` `_` `-`, 중복 금지) · `kind`(필수, `HBLint.{kind}RuleAttribute`) · `description`(선택)은 예약 칸이다.
- 나머지 칸은 어트리뷰트 생성자 매개변수(필수)와 설정 가능한 속성(선택)의 camelCase 이름이다. enum 값은 이름 그대로(`Warning`). 칸 이름 · 값은 대소문자를 가린다.
- JSON은 엄격하게 읽는다 (주석 · 끝 쉼표 없음).
- 생성기는 어트리뷰트를 리플렉션으로 읽으므로 새 규칙 종류(`…RuleAttribute`)를 넣어도 생성기는 고치지 않는다. 다룰 수 있는 값 종류: string · string[] · bool · int · int 기반 enum.

```text
dotnet run --project src/HBLint.Generator.Cli -- generate <rules.json> <LintRules.g.cs> [--check]
dotnet run --project src/HBLint.Generator.Cli -- schema <rules.schema.json> [--check]
```

- 오류가 하나라도 있으면 모두 보여 주고 생성물은 바꾸지 않는다 (종료 코드 1).
- 내용이 같으면 파일을 건드리지 않는다. 출력은 늘 같다 (id 순 · UTF-8 BOM 없음 · LF).
- `--check`는 쓰지 않고 비교만 한다 (줄바꿈 차이는 무시, 다르면 종료 코드 1) — CI에서 원본과 생성물이 어긋났는지 볼 때.
- 어트리뷰트를 바꿨으면 `rules.schema.json`을 다시 만든다.

## 규칙을 어디서 읽나

분석기는 검사 중인 어셈블리 자신과, 그것이 참조하는 어셈블리 중 `HBLint.Attributes`를 참조하는 어셈블리(= 규칙 어셈블리)의 `[assembly:]` 어트리뷰트를 읽는다.

- 규칙 어셈블리를 **직접** 참조하지 않는 어셈블리는 검사하지 않는다 (opt-in). Unity asmdef 참조는 간접으로 이어지지 않으므로 C → B → 규칙 asmdef인 C는 검사되지 않는다.
- 검사 중인 어셈블리가 `HBLint.Attributes`를 참조하지 않아도 된다 (Unity에서 규칙 asmdef만 참조한 경우) — 그때는 규칙 어셈블리 메타데이터에서 직접 읽는다. 규칙 어트리뷰트의 enum은 int 기반만 쓴다.
- 어트리뷰트는 이름으로 찾으므로 어트리뷰트 어셈블리 이름은 `HBLint.Attributes` 그대로 두고, 규칙 파일과 다른 어셈블리에 둔다 (어트리뷰트 .cs를 규칙 파일과 같은 어셈블리에 복사하면 그 어셈블리 안에서만 규칙이 읽힌다).
- `Requires`에 적은 어셈블리를 검사 중인 어셈블리가 모두 참조할 때만 규칙을 적용한다. `Requires`를 통과했는데(비어 있으면 늘 통과) 대상 타입을 못 찾으면 CLL9001 경고를 낸다 (타입 이름 오타). Unity 타입 규칙에 `Requires`를 비우면 UnityEngine이 없는 어셈블리마다 CLL9001이 뜬다.
- 대상 타입 이름은 메타데이터 이름이다: 네임스페이스 포함, 중첩 타입은 `Outer+Inner`, 제네릭은 `` List`1 ``.

## 규칙

| ID | 어트리뷰트 | 검사 |
|---|---|---|
| CLL0001 | `BanNullOperatorRule(type, message)` | 정적 타입이 `type`이거나 그 자식(타입 매개변수 제약 포함)인 식에 `?.` · `??` · `??=` · `is null` · `is not null` (`is not null and var x`처럼 and · or 패턴 안도) |
| CLL9001 | — | 규칙의 대상 타입을 찾을 수 없음 (위치 없는 진단이라 Unity 콘솔에는 안 보인다 — Unity는 생성 단계에서 `[TypeName]` 칸의 타입을 확인해 막는다) |

공통 속성: `Requires`(string[]), `Severity`(`LintSeverity.Info` · `Warning`(기본) · `Error`). 진단 ID는 규칙 종류마다 하나라서 `#pragma warning disable CLL0001`은 그 종류의 규칙을 모두 끈다.

CLL0001이 잡지 않는 것: 정적 타입이 인터페이스 · `object`인 식, `is {}` · `ReferenceEquals`, `switch`의 `null` 갈래. 생성된 코드(`<auto-generated>`)는 검사하지 않는다.


## Unity (UPM 패키지, 6000.3+)

1. `Packages/manifest.json`의 dependencies에 넣는다:
   `"com.hb.lint": "https://github.com/MoewMeowH/CustomUnityToolsCSharp.git?path=HB_Lint/unity/com.hb.lint"`
2. `Tools/HB Lint/설치` — 없는 것만 만든다: `Assets/HBLint/rules.json`(예시 규칙) · `rules.schema.json` · `Assets/HBLint/Rules/CLL.LintRules.asmdef`(HBLint.Attributes 참조, Auto Referenced) · `LintRules.g.cs`.
3. Assembly-CSharp는 자동으로 검사된다. 다른 asmdef는 `CLL.LintRules`를 참조에 넣는다.
4. 규칙은 `Tools/HB Lint/규칙 편집` 창(표 · 상세 칸 · 검증)이나 rules.json을 직접 고친다. rules.json을 저장하면 생성물이 자동으로 다시 만들어진다 (Project Settings > HB Lint에서 끌 수 있음). 오류는 콘솔에 `rules.json(줄,칸) [id] 메시지`로 나오고 생성물은 그대로 남는다.
5. 경로 · 규칙 asmdef 이름 · 자동 생성은 `ProjectSettings/HBLintSettings.asset`(Project Settings > HB Lint).

`Severity = Error`인 규칙은 Unity 컴파일을 막는다. 패키지 에디터 코드는 Assembly-CSharp와 따로라 그때도 편집 창 · 메뉴는 쓸 수 있다.

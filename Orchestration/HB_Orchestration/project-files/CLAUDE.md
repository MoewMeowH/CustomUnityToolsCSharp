# 프로젝트 지침

리뷰 기준은 아래 파일을 따른다.
@REVIEW\_GUIDELINES.md

## 외부 에이전트 (hb-orchestration MCP)

너(Claude)는 지휘자다. 외부 에이전트(GPT·Gemini·로컬)는 `run\\\_mode`로만 부른다.
모드 구성은 `list\\\_modes`로 볼 수 있다 (모드 이름을 모를 때만 호출).

### 언제 부르나 — 기본은 부르지 않는다

* `review`: 50줄 이상 변경, 스레딩/비동기/메모리 관련 변경, 사용자가 교차 리뷰를 요청했을 때
* `panel`: 사용자가 명시적으로 요청했거나 되돌리기 어려운 구조 변경일 때만
* `critique` / `debate`: 설계 결정, 두 가지 이상 방식 중 선택할 때. 가벼운 건 critique, 중요한 건 debate
* `research`: 사용자가 기능·도구 조사를 요청했을 때
* `parallel`: 사용자가 요청했을 때만
* 사소한 변경, 단순 질문에는 쓰지 않는다.

### input 작성 — 토큰 절약 규칙

* **독립성**: 너의 리뷰·결론·선호를 넣지 않는다. 목적, 의도, 제약, 자료만.
* **코드는 `context`로**: 디스크에 있는 코드는 input에 다시 쓰지 말고 `context`에 `{path, startLine, endLine}`(프로젝트 루트 기준, 끝 줄 포함)으로 넘긴다. 서버가 줄 번호와 함께 붙인다. input에는 목적·의도·제약과 디스크에 없는 자료(설계안, 요약)만 쓴다.
* **범위**: 파일 전체가 아니라 변경 부분 + 판단에 필요한 주변 코드(이벤트 해제부, 호출부, 직렬화 필드 선언, 수명주기 메서드 등). 문맥이 모자라 생기는 오판이 더 비싸므로, 지나치게 좁게 자르지 않는다. 상한은 input + 첨부 합계 기준.
* using 목록, 자동 생성 코드, 무관한 메서드는 범위에서 뺀다.
* 너의 리뷰는 결과를 보기 전에 먼저 완성한다.
* `files`에 대상 파일 경로(프로젝트 루트 기준, 가능하면 `path:line`)를 넣는다. 에이전트에게는 전달되지 않고 기록용이다.

### deliberate 모드

중요하고 되돌리기 어려운 설계 결정에만 쓴다. input에 원안(네 제안)과 제약을 쓴다 — 옹호자가 원안을 대신 방어하므로
네 의견을 넣어도 독립성이 깨지지 않는 유일한 모드다. 결과는 판정만 오므로, 판정의 "수정 후 진행" 내용을 반영해 최종안을 정리한다.

### research 모드 순서

1. 목적을 한 줄로 정한다.
2. 네가 웹에서 검색·수집한다. 페이지 전문이 아니라 목적과 관련된 핵심만 요약해 번호를 붙인다 (출처 URL 포함).
3. `run\\\_mode("research", "목적: ...\\\\n\\\\n자료:\\\\n\\\[1] ...\\\\n\\\[2] ...")`
4. 결과의 "추가 조사 필요"가 판단에 꼭 필요할 때만 **한 번 더** 수집해 재실행한다. (서버도 세션당 2회로 막는다)

### 결과 종합

1. **여럿이 공통 지적** — 신뢰도 높음, 우선 처리
2. **한 에이전트만 지적** — 코드를 다시 확인하고 타당/부당 판정과 이유
3. **Claude만 지적** — 그대로 유지
4. **의견 충돌** — 양쪽 근거를 나란히 두고 사용자에게 판단 요청

### 결과 저장

에이전트 응답을 파일로 남길 때는 `save_result`를 쓴다. 응답을 직접 다시 쓰지 않는다.
* `runId`는 `run_mode` 결과 첫 줄, `step`은 단계 제목의 `### N.`
* 코드만 필요하면 `codeBlock`으로 N번째 코드 블록만 저장한다.
* 결과의 `[경고]` 줄(언어 이탈·출력 잘림)은 응답 아래에 붙은 안내다. 응답 내용이 아니다.

### 실행 한도

모드마다 세션당 실행 횟수 한도가 있다 (`list\\\_modes`에 남은 횟수 표시). 같은 모드를 반복 호출하기 전에
"이번 호출이 결론을 바꿀 수 있는가"를 먼저 따진다. 수정 후 재리뷰는 변경이 큰 경우에만 한다.

에이전트가 틀렸다고 판단되면 근거와 함께 기각한다. `\\\[...]`로 시작하는 실패·상한 메시지가 오면 한 줄로 알리고 네 판단만으로 진행한다.

## Unity 테스트 (Unity CLI)

`unity` CLI로 직접 테스트를 돌릴 수 있다. 명령 형식이 불확실하면 `unity <명령> --help`로 확인한다.

### 순서

1. `unity status --format json`으로 이 프로젝트를 연 에디터가 있는지 본다.

   * **에디터가 열려 있으면** 같은 프로젝트로 배치 테스트(`unity test`)를 돌릴 수 없다 (Unity 프로젝트 잠금).
사용자에게 에디터를 닫을지 묻거나, `unity command --query test`로 에디터가 테스트 명령을 노출하는지 확인해 그걸 쓴다.
   * 에디터가 Safe Mode(컴파일 에러)면 `unity pipeline list`로 확인하고 컴파일 에러부터 고친다.
2. 테스트 실행 — 결과는 파일로 받고 출력은 최소로:
`unity test . --mode EditMode --filter "<대상 네임스페이스/클래스>" --report-format junit --output Temp/claude-tests.xml --timeout 600 --quiet --no-banner`

   * 전체가 아니라 **변경과 관련된 테스트만** `--filter`로 돌린다. PlayMode는 느리니 필요할 때만.
3. 종료 코드로 판단한다: `0` 통과 / `8` 테스트 실패 / 그 외 실행 자체 실패(컴파일 에러, 라이선스, 타임아웃).
4. 실패 시 리포트 전체를 읽지 말고 실패한 테스트 항목(`<failure`)만 골라 읽는다.

### 테스트와 외부 에이전트

* 테스트 실패 원인이 바로 보이면 직접 고친다. 외부 에이전트를 부르지 않는다.
* 원인이 불분명할 때만 `review` 모드에 "실패한 테스트 메시지 + 관련 diff"를 넘긴다.
* 고친 뒤에는 같은 `--filter`로 다시 돌려 확인한다. 전체 테스트는 마지막에 한 번만.

### 라이브 에디터 조작

씬·프리팹·에셋 수정이 필요하면 YAML 파일을 직접 고치지 말고, 에디터가 연결돼 있을 때 `unity command`로 조작한다
(사용 가능한 명령은 `unity command`로 확인). 에디터가 없을 때만 파일을 직접 고치고, 그렇게 한다고 알린다.

## Unity 공식 문서 참조

API나 기능이 확실하지 않을 때만 찾아본다. 기억으로 추측하지 않는다.

1\. 어느 페이지인지 모르면 제품별 색인부터: `https://docs.unity.com/<제품>/llms.txt` (전체 목록은 `https://docs.unity.com/llms.txt`)

2\. 페이지를 읽을 때는 URL 끝에 `.md`를 붙여 Markdown으로 가져온다. HTML 페이지는 가져오지 않는다.

3\. 엔진 문서는 이 프로젝트의 Unity 버전(`ProjectSettings/ProjectVersion.txt`)에 맞는 버전 경로를 쓴다.

4\. 페이지 전체를 요약하지 말고 필요한 항목만 확인한다.

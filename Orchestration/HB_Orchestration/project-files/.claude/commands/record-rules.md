공통 `CLAUDE.md`의 "계획서와 작업 로그" · "실수 기록" 세부다. 대상 · 자리 · 언제 적나는 CLAUDE.md에 있다.

## 계획서와 작업 로그

* 1단계 (계획): 코드와 기록을 조사한 뒤 작업 대상 프로젝트 폴더의 `docs/plans/YYYY-MM-DD_제목.md`를 쓴다.
  작업이 여러 저장소 · 프로젝트 폴더에 걸치면 주로 고치는 곳에 두고, 다른 곳의 변경도 계획서에 적는다.
  승인 전에는 코드를 고치지 않는다.
  사용자 결정이 필요한 계획서면 `/plan-share`를 제안한다. 자동으로 올리지 않는다.
  구성: 요약(3줄 이내) / 배경 / 계획 / 버린 대안과 이유 / 위험 / 테스트 / 실제 확인 / 사용자에게 물을 것
  * 위험 실측 (계획서를 쓰기 전에):
    * 조사 뒤 위험 목록(위험마다 의심 정도 · 실측 방법)을 채팅에서 먼저 보이고, 실측 범위(의심되는 것만 · 전부 · 안 함)를 질문 카드로 묻는다.
    * Unity 코드는 HB_Chat 설정에서 '실측 전용'으로 표시한 Unity 프로젝트(방 규칙에 "실측 전용이다"가 있는 연결)에서만 잰다. 연결이 없거나 작업용이면 실측 전용 프로젝트 연결을 요청한다. 작업용 프로젝트에서는 재지 않는다.
    * 그 밖은 scratchpad · 임시 사본 · 읽기 전용 명령 · 기존 시험으로 잰다. 작업 대상 저장소 코드는 고치지 않는다. 시험 서버는 데이터 폴더를 scratchpad로 지정한다.
    * 실측 전에 그 프로젝트의 `git status`를 본다 (깨끗하지 않으면 묻는다). 끝나면 사용자가 남기라고 하지 않은 한 실측이 만든 변경을 되돌리고 실측 전 상태와 같은지 확인한다. scratchpad는 지운다.
    * 실측에 쓴 코드 전문과 결과는 짝 작업 로그 `## 실측` 절에 줄이지 않고 남긴다 (짝 로그는 이때 만든다).
    * 계획서 위험 절에는 위험마다 `확인함`(무엇을 돌렸고 결과 · 로그 링크) 또는 `추정`(실측하지 않은 이유)을 붙인다.
    * 지휘자가 잴 수 없는 위험(Unity 연결 없음 · 사람이 해 봐야 아는 것)은 "사용자에게 물을 것"에 **사람이 확인할 것**으로 따로 묶는다 (직접 시험해 볼 것 · 이미 겪은 일인지).
  * 추정이거나 모르는 것은 지휘자가 나중에 확인할 수 있어 보여도 전부 "사용자에게 물을 것"에 올린다 — 서로 같은 이해인 상태에서 승인받는다.
* 2단계 (결정): 사용자 답을 받으면 계획서 끝에 `## 결정` 절을 덧붙인다.
  * 사용자 답은 원문 그대로 인용한다. 요약하지 않는다.
  * 그 답으로 바뀐 계획 항목을 따로 적는다.
  * 계획 본문은 고치지 않는다.
* 3단계 (결과): 작업 로그는 계획서의 **짝 파일** — 같은 `docs/` 아래 `worklog/<계획서와 같은 이름>.md`에 쓴다 (없으면 만들고 첫 줄에 계획서 링크). 진행 중인 작업 묶음의 로그가 따로 있으면 거기.
  계획과 달라진 것, 테스트, 실제 확인, 리뷰 채택·기각과 그 근거를 적는다. 명령 파일이 말하는 "작업 로그"도 이 짝 파일이다.
  * 색인(같은 `docs/` 아래 `worklog.md`)에는 작업마다 한 줄(날짜 · 작업 · 계획서 · 로그 · 상태)만 두고 상태를 갱신한다.
* 확정과 추정을 구분해 쓴다.

## 실수 기록

`REVIEW_GUIDELINES.md`에는 리뷰 기준(코드에서 찾을 문제)만 두고, 일하다 틀리는 그 밖의 실수는 모두 아래 세 자리에 둔다.
* 지휘자(너): 프로젝트 루트 `MISTAKES.md` (프로젝트 전용, 동기화되지 않음). CLAUDE.md 맨 끝에서 불러온다.
* 서브에이전트: `.claude/mistakes/<서브에이전트>.md` (원본은 HB_Orchestration `project-files`, Sync로 퍼진다).
* 외부 에이전트: HB_Orchestration `project-files/prompts/<역할>/<에이전트>.md` (서버가 그 역할 · 모델의 시스템 프롬프트 끝에 붙인다, HTML 주석은 보내지 않음). 날짜 · 출처는 `(…)` 대신 줄 끝 HTML 주석으로 단다 — 괄호로 쓰면 그대로 보내진다. 본문에 `<!--` · `-->` 문자열(ASCII 화살표 포함)을 쓰면 실행이 거절된다. 골든 사례가 있는 역할에 적었으면 골든 1건으로 확인한다.
* 언제 적나: 사용자가 고쳐 준 것, 같은 실수가 두 번 나온 것, 기각한 지적이 같은 패턴으로 되풀이된 것.
* 서식: 한 줄에 하나 `- 하지 말 것 → 대신 할 것 (YYYY-MM-DD, 출처)`. 훅 · 규칙으로 옮겨진 항목은 지운다.
* 사용자 선호(답 언어 · 표기 등)는 실수가 아니므로 메모리에 둔다.

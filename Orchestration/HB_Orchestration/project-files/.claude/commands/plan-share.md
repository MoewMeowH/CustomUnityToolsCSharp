인자: $ARGUMENTS
- 계획서 경로 하나(프로젝트 루트 기준). 비었거나 파일이 없으면 무엇을 올릴지 한 줄로 묻고 멈춘다.

이 명령은 **사용자가 직접 입력했을 때만** 쓴다. 지휘자는 계획서를 쓴 뒤 이 명령을 제안만 한다 (CLAUDE.md "계획서와 작업 로그" 1단계).
계획서 원문이 회사 밖 서비스(Slack)로 나가므로, 직접 입력했더라도 3단계 확인은 건너뛰지 않는다 (계획서 `Orchestration/HB_Orchestration/docs/plans/2026-10-23_plan-share-명령과-share_guard.md`).

## 실행 형식

모든 slackplan 호출은 Bash 도구에서 **단독 명령**으로 이 형식만 쓴다 (훅 H5 `share_guard.py`가 이 형식을 해석한다. 묶음 · cd · 명령 치환은 막힌다):

```
dotnet run --no-build --project "$SLACKPLAN_ROOT/src/SlackPlanBot" -- <하위 명령> <인자…>
```

- `--no-build`: 켜 둔 수신기가 빌드 출력을 잡고 있어 빌드는 실패한다 (MSB3027).
- 리다이렉트(`2>&1` · `>`)를 붙이지 않는다. 도구가 stdout · stderr를 그대로 받는다 (훅이 막는다).
- 명령줄 글(`--title` 등)은 작은따옴표로 감싸고 `$` · `%` · 백틱 · 작은따옴표를 넣지 않는다. 셸이 펼칠 수 있는 글은 훅이 막는다.
- 결과 판정 (SlackPlanBot README "다른 도구가 읽는 고정 형식"):
  - 성공: 끝 줄 `스레드: <키 | 없음>`, new · revise는 그다음 줄 `판: <해시>`.
  - 실패: 종료 코드 1(사용법 오류 2), stderr `[실패] 원인 한 줄`.
  - `--dry-run`: 끝 줄 `검사: 통과 | 경고 | 막음`, 종료 코드 0 · 3 · 1.
- **조용히 넘어가지 않는다.** 아래 중 하나면 그 자리에서 멈추고 이유를 한 줄로 알린다. 다른 경로로 대신 올리지 않는다.
  - `SLACKPLAN_ROOT` 사용자 환경 변수가 없다 → "SlackPlanBot 저장소 경로를 SLACKPLAN_ROOT 사용자 환경 변수로 등록하고 Claude Code를 다시 열어야 함" (이 저장소가 SlackPlanBot과 상관없는 프로젝트면 이 명령은 쓸 수 없다)
  - `$SLACKPLAN_ROOT/src/SlackPlanBot`가 없다
  - 빌드 결과가 없다 → "SlackPlanBot의 start-listen.bat을 한 번 실행하거나 dotnet build"
  - 종료 코드가 0이 아니다 (dry-run의 3은 예외, 아래 2단계)
  - 성공했는데 고정 줄이 없다
  - 훅이 `[공유 차단]`으로 막았다 → 메시지를 그대로 보인다.

## 순서

1. **확인**: `echo "$SLACKPLAN_ROOT"`로 변수를 보고, 위 실패 조건을 확인한다. 그다음 `find <계획서 경로>`로 이미 올린 스레드를 찾는다.
   - `스레드: 없음` → 2단계에서 `new`
   - 스레드 키가 있다 → 2단계에서 `revise <스레드>` (같은 스레드에 새 판, 승인은 풀린다)
   - 새 스레드로 올리려면 사용자가 그렇게 말했을 때만 `new`를 쓴다.
2. **dry-run**: `new <계획서> --title '<제목>' --dry-run` 또는 `revise <스레드> <계획서> --dry-run`.
   - 제목은 계획서 첫 `# ` 줄에서 가져온다. 위 "명령줄 글" 규칙에 걸리는 글자는 빼고 쓴다.
   - dry-run은 **봇 검사 결과만** 보인다. 훅 H5는 dry-run을 통과시키고 아무것도 출력하지 않는다 — 훅이 막는 것(프로젝트 패턴 · 개인 값 · 무시 폴더 · 파일 이름)은 4단계에서 처음 드러난다.
   - `검사: 막음`(1) → 걸린 줄을 보이고 멈춘다. 계획서에서 빼는 것은 사용자와 정한다.
   - `검사: 경고`(3) → 걸린 줄을 보이고 멈춘다. 지휘자는 **`--allow-warnings`를 스스로 붙이지 않는다** (훅도 막는다). 넘길지는 사용자가 정하고, 넘길 때는 사용자가 `!` 명령으로 직접 올린다.
3. **사용자 확인**: 아래를 보이고 "올릴까요?"로 묻는다. 답이 오기 전에는 올리지 않는다.
   - 제목 · 계획서 원본 경로 · 줄 수 · 새 스레드인지 같은 스레드 새 판인지
   - dry-run에서 걸린 줄(봇) 원문 그대로. 없으면 "없음". "올릴 때 훅이 프로젝트 패턴 · 개인 값으로 한 번 더 검사함"도 함께 적는다.
   - 본문 요약 3~5줄 (지휘자가 쓴 요약이므로, 사용자가 원본을 직접 열어 볼 수 있게 경로를 같이 둔다)
4. **올리기**: 2단계 명령에서 `--dry-run`만 뺀 명령. 끝 줄 `스레드:` · `판:`을 확인한다.
   - 훅이 `[공유 차단]`으로 막으면 그 줄을 그대로 보이고 멈춘다. 계획서에서 빼거나 사람이 `!`로 올린다.
   - 받은 함의 "새 대화 요청"에 계획서를 답으로 붙이는 흐름(`new … --thread <채널_ts> --item <항목>`)도 같은 순서다. 두 값은 ID 모양이어야 한다.
5. **기록**: 작업 로그에 "Slack 공유 판 <해시>" 한 줄만 남긴다. **스레드 키 · 채널 ID · 링크는 이 프로젝트의 파일에 쓰지 않는다** (다시 찾을 때는 `find`). 사용자에게는 판 해시와 "답 · 승인은 `/plan-check <계획서>`로 확인"을 알린다.

# /preflight — 실행 전 점검

큰 작업(설계 변경, 수명주기·스레드·비동기·성능 핫패스를 건드리는 변경)을 실행하기 전에 쓴다.
단계를 한 번에 돌리지 않는다. **단계마다 멈추고 사용자에게 보고한 뒤, 사용자가 "다음"이라고 하면 넘어간다.** 이 불편함은 의도한 것이다.

요청: $ARGUMENTS

## 쓰기 전에: 이 명령이 맞는지

| 상황 | 쓸 것 |
|---|---|
| 작은 변경, 한 파일 안의 수정 | `review` |
| 성능만 보고 싶을 때 (핫패스, 할당, 동기화) | `perf_sol` (기본) / `perf_astra` (중요한 핫패스) / `perf_argon` (다른 회사 시선) |
| 설계 방향 하나만 비판받고 싶을 때 | `critique` |
| 여러 파일·구조를 바꾸는 큰 작업, 되돌리기 비싼 작업 | **이 명령** |

대상은 코드, 계획서, 설계안 중 무엇이든 된다. 아직 코드가 없으면 P3·P5는 코드 대신 최종 설계안을 다룬다.
이 명령이 맞지 않아 보이면 시작하기 전에 사용자에게 다른 모드를 제안한다.

## 공통 규칙

- 시작 전에 대시보드의 오늘 비용·토큰 상한 칸을 사용자에게 확인받는다. preflight 한 번은 일일 상한(`Budget.DailyCostLimitUsd` · `Budget.DailyTokenLimit`)의 상당 부분을 쓴다 (2026-10-18 실측: 약 $1.1 · 37만 토큰). 상한은 실행 전에 검사하므로 중간 단계에서 거절될 수 있다.
- 모든 `run_mode` 호출에 `reason`을 쓴다. `ownReview`가 필수인 단계(P1, P5)는 결과를 보기 전에 ownReview를 작업 로그에 다 쓴 뒤 호출한다.
- 모델에게 넘기는 원문은 손으로 옮겨 적지 않는다. 산출물을 파일로 저장하고 `context`에 경로로 붙인다. 에이전트 응답은 `save_result`로 저장한다.
- 각 단계 산출물은 `docs/preflight/<날짜>_<주제>/` 아래에 `request.md`(요청 원문), `attachments/`, `p1_A.md`, `p1_B.md`, `p1_Perf.md`, `p2_A.md`, `p2_B.md`, `p3_A.md`, `p3_B.md`, `p4_report.md`, `final_code/`, `p5a_check.md`, `p5b_perf.md`로 저장한다.
- `context`는 폴더를 받지 않는다. 파일마다 `{path, startLine: 1, endLine: <끝 줄>}`로 넘긴다 (끝 줄은 직접 센다).
- 결과가 마음에 들지 않는다고 다시 돌리지 않는다. 인프라 실패(타임아웃, 응답 없음)만 예외로 하고, 그때는 첫 시도도 `_run1`로 보관한다. 모드의 세션당 실행 한도(2회)는 이 재시도 한 번을 위한 여유다.
- 모델끼리 합의했다는 사실은 증거가 아니다. 판정은 근거로만 한다.

## 첨부 (있을 때)

- xlsx·xlsm·csv: `python .claude/scripts/xlsx_dump.py "<파일>"`의 출력을 `attachments/<파일 이름>.md`로 저장하고, 그 파일을 `context`로 붙인다. csv도 직접 붙이지 않고 도우미를 거친다 (CP949 등 인코딩 처리).
  - 표가 잘렸다는 안내가 나오면 필요한 시트만 `--max-rows`를 늘려 다시 뽑는다.
  - 스크립트가 `[오류]`로 끝나면 그 메시지를 한 줄로 알리고 멈춘다.
- 이미지(도우미가 뽑은 것 포함)·pdf·docx는 지휘자가 직접 읽고, 판단에 필요한 내용만 요약해 `attachments/<파일 이름>_요약.md`로 저장해 붙인다. 열어 보지 못한 것은 못 봤다고 적는다.
- 첨부 요약 파일은 P1, P3, P5에 붙인다 (요청 원문의 일부로 본다). P3는 최종 수정안을 쓰므로 첨부의 사양을 봐야 한다. P2는 P1 지적을 판정만 하므로 붙이지 않는다.
- `perf_*` 단독 모드에도 같은 규칙을 쓴다.

## P1 — 독립 검토 (`preflight_p1`)

- context: `request.md`, 첨부 요약, 대상 코드 전체, 계획서·설계안(있으면).
- 검토자 A, B, 성능 검토자가 서로 결과를 보지 않고 동시에 검토한다.
- 결과는 단계 1·2·3을 `p1_A.md`, `p1_B.md`, `p1_Perf.md`로 저장한다.
- 끝나면 보고: 세 검토의 지적 수, 서로 겹친 것과 한쪽만 찾은 것, 설계 방향 판단(유지 / 수정 / 재설계)이 갈렸는지. **멈춘다.**

## P2 — 상호 판정 (`preflight_p2`)

- input 첫머리에 첨부 이름표를 쓴다: `p1_A.md = 검토자 A / p1_B.md = 검토자 B / p1_Perf.md = 성능 검토자`. 에이전트에게는 파일 경로가 제목으로 가고, 프롬프트는 "검토자 A" 같은 이름으로 부르기 때문이다.
- context: `request.md`, `p1_A.md`, `p1_B.md`, `p1_Perf.md`.
- 끝나면 보고: 판정 표 요약, 원문을 바꿔 인용한 곳이 있는지(지휘자가 원문과 대조), 미해결 쟁점, 사용자 질문.
- **사용자 확정을 받는다.** 질문에 대한 답을 `confirmed.md`로 저장한다. 사용자가 "미정"이라고 하면 미정으로 적는다. **멈춘다.**

## P3 — 최종 수정안 (`preflight_p3`)

- input: P2와 같은 이름표 + `p2_A.md = 검토자 A의 Phase 2 / p2_B.md = 검토자 B의 Phase 2` + `confirmed.md` 내용.
- context: `request.md`, 첨부 요약, `p1_*.md` 셋, `p2_*.md` 둘.
- 입력이 상한(`MaxInputChars`)을 넘어 거절되면 요청·첨부 요약·확정 사항은 그대로 두고, P1 원문 중 판정에서 다룬 항목만 남긴 범위로 줄인다. 줄인 범위는 작업 로그에 적는다.
- 끝나면 보고: 두 수정안의 차이(구조, 범위 확장, 성능 지적 반영 내역), 자기 보고 수치를 지휘자가 직접 센 값과 대조한 결과(완성본·diff일 때), 확정 사항 대조표에서 빠진 번호나 "미반영"이 있는지, 출력 잘림 `[경고]`가 있었는지. **멈춘다.**

## P4 — 지휘자 종합 (모드 없음)

- 지휘자가 직접 쓴다. 모델에게 종합시키지 않는다(자기 안을 자기가 판정하게 된다).
- 두 수정안 중 하나를 고르거나 합쳐 **최종 코드 하나**(코드가 없는 작업이면 최종 설계안 하나)를 `final_code/`에 둔다. 고른 이유와 버린 것을 `p4_report.md`에 쓴다.
- 최종 코드가 컴파일되는지 확인할 수 있으면 확인한다.
- **대조 단계 (P5 전, 모델 호출 없음):** 최종 코드를 다 쓴 뒤 `p4_report.md`에 대조표를 쓴다. 합치면서 요구사항이 빠지는 것을 막는다.
  - `confirmed.md`의 확정 사항 전부: | 확정 번호 | 최종 코드 위치(파일:줄) | 확인 방법(코드 확인 · 테스트 이름) | 결과 |. 확정 사항이 여러 곳(예: 런타임 클래스와 생성 템플릿)에 걸치면 곳마다 한 줄.
  - P3 두 안의 확정 사항 대조표와 고른 이유 표의 채택 항목도 같은 형식으로 맞춰 본다.
  - 위치를 찾지 못한 항목은 고친 뒤 다시 대조한다. 일부러 뺀 것은 "버린 것"에 이유를 쓴다.
  - 대조표는 P5에 붙이지 않는다 (P4 보고서의 일부).
- 끝나면 보고(대조에서 빠져 있다가 고친 항목 수 포함)하고 **멈춘다.** 사용자가 최종 코드를 확인한 뒤 P5로 간다.

## P5 — 최종 검사 두 개

P5a와 P5b는 서로 결과를 보지 않는다. 둘 다 **P1~P3의 검토 원문, P4 보고서, 지휘자의 의심 지점을 붙이지 않는다.** 붙이면 앞에서 좁혀진 범위를 그대로 물려받는다. 이 첨부 규칙이 이 명령의 핵심이다.

### P5a — 전체 최종 검사 (`preflight_check`, astra)

- **첨부는 셋만:** `request.md`(+ 첨부 요약), `confirmed.md`, `final_code/`의 파일들(최종 코드 또는 최종 설계안).
- PF1 목록도 붙이지 않는다. 성능은 P5b가 본다.
- 보는 것: 회귀, 확정 사항 위반, 정확성·생명주기·동시성, 기각 여부와 수정 방향.

### P5b — 성능 검사 (`preflight_perf`, sol)

- **첨부는 넷만:** `request.md`(+ 첨부 요약), `confirmed.md`, `final_code/`의 파일들, `p1_Perf.md`의 지적 목록(1번 표만 — 줄 범위로 지정).
- 보는 것: 새로 생긴 성능 문제, PF1 반영 여부, 측정 우선순위.

### 공통

- 결과는 P5a를 `p5a_check.md`, P5b를 `p5b_perf.md`로 저장한다.
- 호출 전에 각각의 첨부 목록을 작업 로그에 적는다.
- 각각 한 번만 돌린다. P5 지적으로 고친 뒤 P5를 다시 돌리지 않는다. 다시 돌릴지는 사용자가 정한다.
- 끝나면 둘을 나란히 보고한다: 새로 찾은 문제, 확정 사항 위반, PF1 반영 확인, 두 결론(전체 / 성능). 결론이 갈리면 그대로 보고하고 지휘자가 고르지 않는다. **멈춘다.**

## 마무리

- 단계별 호출 시각, runId, 비용(대시보드 기준)을 작업 로그에 남긴다.
- 커밋은 사용자가 요청할 때만 한다.
- 한 세션에서 preflight는 한 번만 한다. 다른 작업을 점검하려면 새 세션을 연다(실행 한도가 세션 단위라서, 두 번째 점검은 재시도 여유를 잃는다).

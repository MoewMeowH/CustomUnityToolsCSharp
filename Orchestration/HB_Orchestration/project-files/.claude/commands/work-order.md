인자: $ARGUMENTS
- 요청 문장과 첨부 경로(xlsx·xlsm·csv 등 실제로 있는 파일)를 가른다. 요청이 비어 있으면 무엇을 맡길지 한 줄로 묻고 멈춘다.

이 명령은 **지시서만 만든다.** 대상 프로젝트의 코드·설정·규칙서는 고치지 않고, 계획서(docs/plans)도 쓰지 않는다. 계획서와 구현은 이 지시서를 받은 실행 세션이 한다.

## 순서

1. **첨부 검토** (첨부가 있을 때)
   - xlsx·xlsm·csv: `python .claude/scripts/xlsx_dump.py "<파일>"`. 표·병합 셀·메모·텍스트 상자 글이 Markdown으로 나오고, 이미지는 `review_tmp/work-order/<파일 이름>/`에 저장된다.
   - 출력에 적힌 이미지 중 요청과 관련 있어 보이는 것은 직접 열어 본다. "열 수 없는 형식"은 열어 보지 못했다고 지시서에 적는다.
   - 표가 잘렸다는 안내가 나오면 필요한 시트만 `--max-rows`를 늘려 다시 읽는다. 전체를 한 번에 덤프하지 않는다.
   - 스크립트가 `[오류]`로 끝나면 (openpyxl 없음, .xls 등) 그 메시지를 사용자에게 한 줄로 알리고 멈춘다.
   - 다른 형식(pdf·이미지·docx)은 직접 읽는다.
   - `work_order_main` 검토자에게도 이미지를 보여야 하면 CLAUDE.md "이미지 첨부" 절차(collect → 사용자 정리 → shrink → `images`)를 따른다.
2. **대상 조사 (읽기 전용)**: 요청한 기능을 연결할 위치 후보를 찾는다 (`파일:줄`). 구현 방법을 정하지 말고, 실행 세션이 확인해야 할 곳과 의심 지점만 모은다.
3. **초안 작성**: 아래 양식으로 쓴다. `그외 이상사항`은 비워 둔다.
   - 확정한 사실과 추정을 구분한다. 의심 지점은 전부 추정으로 쓴다.
   - `원칙`의 첫 줄은 항상 넣는다. 나머지 원칙은 이 요청에 해당될 때만 넣거나 새로 쓴다.
   - `위험이 큰 항목`의 번호는 네가 판단해 채운다. 없으면 그 줄을 뺀다.
4. **자체 검토 먼저**: 결과를 보기 전에 초안의 빈틈(요청 누락·범위 초과, 절 사이 불일치, 근거 없는 의심 지점, 빠진 완료 기준)을 직접 정리한다. 이것이 `ownReview`다.
5. **`run_mode("work_order_main")`**
   - input: `## 사용자 요청 (원문)` + `## 첨부 요약` (있을 때) + `## 지시서 초안` (`그외 이상사항` 절 제외)
   - context: 조사에서 근거로 쓴 코드 범위 (선택, 필요한 만큼만)
   - reason: 부른 이유 한 줄
   - ownReview: 4의 원문
   - 이 모드는 **초안 자체가 검토 대상**이라, 네 판단(의심 지점 포함)을 input에 넣는다. 다른 모드의 독립성 규칙과 다르다.
6. **`그외 이상사항` 작성**: 두 검토와 네 자체 검토를 묶는다.
   - 공통 지적 → 반영하고 `반영:`으로 남긴다.
   - 한 검토만 지적 → 코드나 첨부를 다시 확인한 뒤 `반영:` 또는 `기각:` + 근거.
   - 네 자체 검토에만 있음 → 반영한다.
   - 의견 충돌 → 양쪽 근거를 나란히 적고 `사용자 판단 필요`로 남긴다.
   - 반영한 지적은 해당 절도 고친다. 검토자가 사용자에게 물으라고 한 것은 `사용자 판단 필요`에 모은다.
   - `[`로 시작하는 실패·한도 메시지가 오면 `검토 실패: <메시지>`라고 적고 완성한다. 재시도는 사용자가 원할 때만 한다.
7. **저장·출력**
   - 폴더: `list_modes` 결과에 `지시서 폴더: <경로>` 줄이 있으면 그 경로, 없거나 `[주의] WorkOrders.Folder`면 `docs/work-orders/`. 프로젝트 루트 기준이다.
   - 파일 이름: `YYYY-MM-DD_HHmm_<제목>.md` (제목은 요청을 줄인 말, 공백은 `-`). 이미 있으면 덮지 않고 끝에 `_2`를 붙인다.
   - UTF-8로 저장한 뒤 지시서 전문을 대화에 출력하고, 마지막 줄에 저장 경로를 적는다.

## 양식

```markdown
# 작업 지시서: <요청 한 줄>

## 목적
<요청을 이해한 내용과 최종 목적>

대상: <대상 프로젝트 / 폴더 / 파일:줄>

## 진행 방식
- 첨부 <파일명>을 먼저 읽고 검토한다. (이미지: <폴더>)
- 대상 프로젝트에서 이 기능을 연결할 위치를 검토한다.
- 코드를 먼저 조사하고 계획서만 낸다: docs/plans/YYYY-MM-DD_제목.md. 승인 전에는 코드를 고치지 않는다.
- 아래 의심 지점은 확인 전 추정이다. 확정 / 기각 / 범위 조정을 근거와 함께 계획서에 적는다.
- 항목마다 구현 → 컴파일 확인 → 테스트 → 커밋.
- 위험이 큰 항목(<번호>)은 review로 검토받는다. reason 필수. ownReview는 결과를 보기 전에 네가 직접 찾은 것으로 채운다.
  - 아래 의심 지점과 그외 이상사항은 에이전트 input에 넣지 않는다 (독립성 유지).

## 원칙
- 옵션은 비워 두면 기존 동작과 같다.
- <이 요청에 맞는 원칙>

## 의심 지점 (추정)
1. <위치> — <의심 내용> / <왜 의심하는지> / <확인 방법>

## 함께 확인할 것
- 이 지시서는 work_order_main(gpt_mini_luna · gemini_main_flash)로 검토받았다 (runId <값>).
- <실행 세션이 사용자에게 먼저 확인할 것, 계획서에서 답할 것>

## 그외 이상사항
- 반영: <지적> — <어느 절을 어떻게 고쳤나> (<출처: 공통 / luna / flash / Claude>)
- 기각: <지적> — <근거>
- 사용자 판단 필요: <쟁점> — <양쪽 근거>
```

- 첨부가 없으면 `진행 방식`의 첫 줄을 뺀다.
- 원칙 후보 (해당될 때만): `실패는 예외가 아니라 {"ok":false,"error":"..."} JSON으로 돌려준다.` (도구·API형 작업) / `패널(사람용) 동작은 바꾸지 않는다. 바꿔야 하면 계획서에 이유를 적는다.` (사람용 UI가 있을 때)

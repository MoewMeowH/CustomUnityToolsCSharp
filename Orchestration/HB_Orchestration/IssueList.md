입력 2: 디버깅 (Unity 6 / Job System · Burst)
필수
1. 검토 대상

* 종류: 버그 상황 + 코드
* 증상:

"에디터에서 실행하면 가끔 InvalidOperationException이 나고, 빌드에서는 예외 없이 cell0 값이 실행마다 달라져요. 그리고 씬을 닫을 때 간헐적으로 에러가 떠요."

* 코드:

csharp

```csharp
using Unity.Burst;
using Unity.Collections;
using Unity.Jobs;
using Unity.Mathematics;
using UnityEngine;

public class BoidSystem : MonoBehaviour
{
    [SerializeField] private int count = 20000;

    private NativeArray<float3> _positions;
    private NativeArray<float3> _velocities;
    private NativeArray<int> _cellCounts;
    private JobHandle _handle;

    void Start()
    {
        _positions  = new NativeArray<float3>(count, Allocator.TempJob);
        _velocities = new NativeArray<float3>(count, Allocator.TempJob);
        _cellCounts = new NativeArray<int>(1024, Allocator.Persistent);

        for (int i = 0; i < count; i++)
            _positions[i] = UnityEngine.Random.insideUnitSphere * 50f;
    }

    [BurstCompile]
    struct CountJob : IJobParallelFor
    {
        [ReadOnly] public NativeArray<float3> positions;
        public NativeArray<int> cellCounts;

        public void Execute(int i)
        {
            int cell = (int)(math.abs(positions[i].x) % 1024);
            cellCounts[cell]++;
        }
    }

    [BurstCompile]
    struct MoveJob : IJobParallelFor
    {
        public NativeArray<float3> positions;
        [ReadOnly] public NativeArray<float3> velocities;
        public float dt;

        public void Execute(int i)
        {
            positions[i] += velocities[i] * dt;
        }
    }

    void Update()
    {
        var countJob = new CountJob { positions = _positions, cellCounts = _cellCounts };
        var h1 = countJob.Schedule(_positions.Length, 64);

        var moveJob = new MoveJob
        {
            positions = _positions,
            velocities = _velocities,
            dt = Time.deltaTime
        };
        _handle = moveJob.Schedule(_positions.Length, 64, h1);
    }

    void LateUpdate()
    {
        _handle.Complete();
        transform.position = _positions[0];
        Debug.Log($"cell0={_cellCounts[0]}");
    }

    void OnDestroy()
    {
        _positions.Dispose();
        _velocities.Dispose();
        _cellCounts.Dispose();
    }
}
```

2. 목표

* 위 세 가지 증상(에디터 예외, 빌드에서 cell0 값 불일치, 씬 종료 시 간헐적 에러)의 원인을 찾고, 근본 원인을 해결하는 수정안을 얻는 것.

3. 제약조건

* 언어/버전: C# 9, Unity 6 (6000.x)
* 사용 기술: Job System, Burst, Unity.Collections (NativeArray)
* 유지해야 할 것: 개체 수(약 20000)에서 Job 기반 병렬 처리 구조는 유지 (메인 스레드 단일 처리로의 후퇴는 불가)
* 환경 차이: 증상이 에디터와 빌드에서 다르게 나타남
* 확인하지 못한 것: 이 코드를 Unity에서 실제로 컴파일·실행해본 적은 없음

있으면 좋은 것
4. 성공 기준

* 세 증상이 각각 어떤 원인에서 오는지 구분되어 설명될 것.
* 에디터 예외를 단순히 억제하는 방식이 아니라, 에디터와 빌드 양쪽에서 결과가 결정적(deterministic)으로 나오는 수정안일 것.

5. 현재 의견/가설

* 없음 (독립 검토 상태로 진행)

# GPT Phase 1 접수와 양쪽 종합 (샘플 2)

## 1. 접수

유효한 Phase 1 응답이야. P-01~P-08, 증상 대응표, 6개 항목이 갖춰져 있고 수정 코드도 있어. GPT think 모드, 시간은 2분 54초, 토큰은 모름으로 기록할게.

형식상 이상한 점은 둘이야.
- 본문에 `【turn…search…】` 같은 인용 표식이 있는데 링크로 풀리지 않아. 검색은 한 것 같지만 **출처를 내가 확인할 수 없어서** 근거로 쓰지 않아.
- "반박 대상이 되는 정확한 주장"이 코드나 사용자 보고에 없는 가상의 주장이야(예: P-03의 "같은 프로그램을 실행하면 동일한 초기 위치가 만들어진다"). 반박할 상대 의견이 없는 단계라 생긴 현상이고, 내용 판정에는 영향 없어.

## 2. 쟁점 정규화 (두 모델 Phase 1 대조)

| ID | 내용 | Gemini | GPT | 상태 |
|---|---|---|---|---|

| S2-02 | 장기 보관 배열에 `TempJob` | G-02 | P-04 | **SUPPORTED** |
| S2-03 | `Complete()` 없이 `Dispose()` | G-03 | P-05 | **SUPPORTED** |
| S2-04 | `UnityEngine.Random` 시드 미고정 | G-04 | P-03 | **SUPPORTED** |
| S2-05 | 프레임마다 카운트 미초기화(누적), 속도 전부 0 | G-05 | P-02, P-07 | **SUPPORTED**. 누적이 의도인지는 **OPEN** |

## 3. 수정안 비교 (줄 수는 두 응답 파일의 코드 블록을 직접 센 값)

| | Gemini | GPT |
|---|---|---|
| 줄 수 | 128줄 (빈 줄 제외 108) | 265줄 (빈 줄 제외 211) |
| 카운팅 방식 | `Interlocked` 원자 증가 + 프레임마다 `ClearCountsJob` | 파티션별 히스토그램 → 셀별 병렬 축약 |
| `unsafe` | 필요 (메서드 2개) | 키워드 없음 |
| 추가 메모리 | 없음 | 약 316 KiB (79×1024 정수. 내가 계산해 맞음) |
| 난수 | `Unity.Mathematics.Random`으로 교체 (분포가 원본과 달라짐) | 원본 분포 유지, 전역 난수 상태 복구 |
| 속도 | 임의로 5f 방향 부여 | 0 유지 (원본 동작 보존) |
| 알려진 위험 | S2-07 (Burst 동작·`unsafe` 허용 설정) | 코드 길이, 파티션 행 독점 가정 |

- 줄 수는 Gemini가 짧고 Burst/`unsafe` 위험을 안고 있어. GPT는 길지만 `unsafe` 없이 경쟁 자체를 구조로 없앤 안이야.
- 난수 방식은 서로 일장일단이 있어. 에디터와 빌드 사이의 결정성만 보면 `Unity.Mathematics.Random`이 알고리즘이 고정돼서 유리할 수 있고, GPT 방식은 원본 분포를 보존하는 대신 Unity 버전·플랫폼 간 동일성을 보증하지 않는다고 스스로 밝혔어. 둘 다 테스트 전까지 우열을 가리지 않을게.
- 어느 쪽도 컴파일하지 않았어. **채택 결정은 Phase 5로 넘겨.**

## 4. 샘플 1과 다르게 보인 점

- **규칙 A 준수**: GPT는 예외 타입을 "스택 트레이스 없이는 확정 불가"로 일관되게 유보했어. Gemini는 `[사실]`로 단정하고 본문 안에서도 모순됐어(인덱스 위반이라면서 `InvalidOperationException`이라고 함).
- **자체 모순**: Gemini 검증 방법은 "합이 20000보다 작게 나옴"이라는데 같은 응답에서 누적이라고 했어.
- **범위 준수**: Gemini는 질문으로 올린 속도 사양을 코드에서는 이미 가정했어. GPT는 원본 동작을 보존했어.
- **줄 수 자기보고**: 이번에는 두 모델 모두 줄 수를 주장하지 않아서 비교할 자기보고가 없어.
- 두 모델 모두 새 대화, 페르소나 없음, 모드 고정이라는 통제는 지켜졌다고 기록할게. GPT만 검색을 쓴 흔적이 있어서(인용 표식) 이건 변수로 남겨.

# GPT Phase 2 접수 (샘플 2)

## 1. 접수

유효한 Phase 2 응답이야. P2-01~P2-13 ID가 있고, Gemini의 G-01~G-06을 개별 판정했고, 상대 수정 코드 검토, 자신의 Phase 1 수정, 미해소 쟁점, 사용자 질문이 모두 들어 있어. 입력도 Gemini Phase 1 원문만 쓴 것으로 보이고, 네 확정 답변이 반영되지 않은 상태여서 Gemini Phase 2와 정보 조건이 같아. 기록은 GPT think, 3분 3초, 토큰 모름이야. 인용 표식(`【turn…】`)은 이번에도 링크로 풀리지 않아서 출처로 쓰지 않아.

## 2. 쟁점별 판정

## 3. 내가 본 포인트

**① 핵심 불일치가 생겼어 (S2-09).** 두 모델이 증상 1의 원인을 서로 다르게 보고 있어.
- **Gemini P2**: 인덱스 위반이면 거의 매번 `IndexOutOfRangeException`이 날 텐데, 사용자는 `InvalidOperationException`이 가끔 난다고 했으니 증상 1은 생명주기 경로일 수 있다.
- **GPT P2**: `InvalidOperationException`이 난다면 잘못된 인덱스 접근 자체를 우선 확인해야 하고, 병렬 인덱스 접근 위반이 유력하다. 단 스택 트레이스 전에는 확정할 수 없다.
- 내 생각은 Gemini 쪽 논리가 더 설득력 있어 보이지만, 확정이 아니라 추론이야. **이건 Phase 5에서 스택 트레이스로만 판가름 나.** 한쪽을 채택하지 않고 NEEDS_TEST로 둘게.

**② GPT의 따옴표 인용 일부는 요약본이야.** P2-10은 Gemini가 "고정 dt로 완전한 결정성을 확보할 수 있다"고 주장한 것처럼 적었는데, 실제 원문은 코드 주석의 "완전 결정론이 필요할 경우 고정 dt 사용 권장"이야. 주장을 조금 강하게 바꿔서 반박한 셈이야. 다만 결정성의 세 층위를 구분한 내용 자체는 타당해서, 새로운 사양 쟁점(S2-20)으로 살렸어.

**③ GPT의 Phase 1 수정은 대부분 실질 철회가 아니야.** 섹션 5의 수정 항목 중 P-01은 이미 유보했던 내용이고, 일부는 Gemini가 한 말을 자기 수정처럼 적었어. 실질적인 변경은 P-02의 "프레임별 통계가 의도"라는 가정을 조건부로 낮춘 정도야. GPT Phase 1이 대체로 맞았기 때문일 수 있어. 두 모델의 철회 건수 차이(Gemini 4건, GPT 약 1건)는 모델의 정직성이 아니라 처음 답의 정확도 차이로 읽을게.

**④ Update 시작 부분의 `Complete()`에 대해 두 모델이 다르게 말했어.** Gemini는 GPT 코드에 없다며 하드닝을 요구했고(G2-09), GPT는 Gemini 코드에 있는 걸 중복에 가깝다고 했어(P2-06). 둘 다 해가 없다는 점은 동의하고, 필수는 아니라는 점에서 S2-16을 OPEN(낮음)으로 유지할게.

GPT가 새로 올린 질문이야. 네 성공 기준의 "결정적"이 정확히 무엇을 뜻하는지가 수정안 범위를 갈라.

- **(a)** 같은 시드, 같은 시뮬레이션 틱 수에서 같은 결과면 충분하다
- **(b)** 프레임 레이트가 달라도 같은 경과 시간에서 결과가 같아야 한다 (고정 시간 간격과 틱 관리까지 필요)

지금 속도가 0이라 (a)와 (b)는 현재 코드에선 차이가 안 나지만, 속도를 넣는 순간 갈려. 모르면 "미정"이라고 답해도 돼.

## 7. 진행 안내

1. 6항 질문에 답해줘(미정이어도 됨). 답이 없으면 블록 5번은 "미정" 그대로 쓰면 돼.
2. 두 프롬프트를 각각 새 대화에 보내줘. G3에는 **GPT Phase 2**, P3에는 **Gemini Phase 2** 원문을 넣어야 해. 서로 헷갈리지 않게 주의해줘.
3. 샘플 1에서 줄 수와 상태 수 자기보고가 부정확했던 점이 있어서, 이번에도 4번 항목으로 모델의 자기보고를 받아 둘게. 내가 코드 블록을 직접 세서 비교할 거고, 이 비교 방식은 모델에게 알리지 않았어.

이에 대한 나의답은
"결정적(deterministic)"의 의미는

* (a)로 확정: 같은 시드, 같은 시뮬레이션 틱 수에서 같은 결과가 나오면 충분해.
* (b) 프레임 레이트 독립성과 (c) 플랫폼 간 비트 단위 동일성은 이번 범위 밖이야. 속도가 채워지는 시점에 다시 검토할 사항으로 미해결 쟁점에 남겨줘.
* 성공 기준의 원래 의도는 "에디터와 빌드 양쪽에서, 병렬 쓰기 경쟁 때문에 실행마다 `cellCounts` 값이 달라지는 일이 없을 것"이었어. 스레드 스케줄링에 따라 결과가 흔들리지 않는 것이 핵심이고, 시간 관리 체계까지 요구한 건 아니야.

## 5. GPT P3에서 내가 본 점

**좋은 점**

- 확정 사항 5를 넘어서지 않고 (b), (c)를 미해결로 남겼어.

**주의할 점**
- **`Unspecified` 기본값 (S2-25)**: 사용자가 미정이라고 한 걸 존중한 설계지만, Inspector에서 모드를 고르기 전에는 컴포넌트가 아무것도 안 하고 꺼져. 테스트에 번거롭지만 임의 가정을 막는 장점도 있어. 어느 쪽이 좋은지는 사용자 선택이야.
- **`int` → `long` (S2-26)**: 누적 모드 오버플로를 막는 방어지만 원본 타입을 바꾼 범위 확장이야. Gemini는 같은 문제를 미해결 쟁점으로만 기록했어.
- **비유한 좌표 제외 정책 (S2-27)**: 제외할지 별도로 셀지는 사양에 달렸다고 GPT도 인정했어. 코드가 늘어난 만큼 범위 확장이기도 해.

- `Update()` 안의 `_handle` 중간 대입 두 번은 마지막 대입으로 덮여서 불필요해. 동작에는 영향 없어.

## 3. 채택·기각한 반박과 이유

**채택**
- 데이터 레이스는 안전성 검사가 직접 탐지하는 게 아니라는 교정(GPT P2-01). 근거: 검사 대상은 병렬 반복의 쓰기 인덱스 범위야.
- `Unity.Mathematics.Random`의 반지름 선형 추출은 `insideUnitSphere`와 분포가 달라진다는 지적(GPT P2-04). 코드 논리로 확인돼서 Gemini도 철회했어.
- 임의로 넣은 속도는 원본 동작을 바꾸는 범위 초과였다는 지적(GPT P2-07).
- 장기 보관 배열에 `TempJob`을 쓴 건 수정 대상이지만 보고된 에러의 원인으로는 단정 못 한다(GPT P2-02).
- `unsafe`와 포인터 방식은 사용자 제약으로 제외. Phase 1에는 없던 후행 제약이라 Gemini Phase 1의 결함으로는 세지 않았어.

**기각 또는 보류**
- Gemini의 성능 수치("0.02ms", "수십 μs")는 근거가 없어서 기각했고 Gemini도 철회했어.
- Gemini G2-10의 "`NativeDisableParallelForRestriction`을 쓰면 에디터 검사가 무력화되어 네이티브 크래시"는 단정으로 보기 어려워서 증거로 쓰지 않았어. 일반 조언(인덱스 방어)만 반영했어.
- GPT P2-10의 "고정 dt로 완전한 결정성을 확보할 수 있다는 주장"은 Gemini 원문의 요약본에 대한 반박이었어. 결정성의 층위를 구분한 건 유용했지만, 사용자 결정(a)로 범위 밖이 됐어.
- 두 모델이 같은 결론에 도달했다는 이유로 채택한 항목은 없어.

## 4. 수정 설계 방향

**공통 골격 (두 모델이 같은 구조로 수렴, 단 일치는 증거가 아님)**
1. 개체별 셀 인덱스를 `IJobParallelFor`로 `_cellIndices[i]`에 기록해 쓰기 경쟁을 구조적으로 제거한다.
2. 단일 `IJob`이 인덱스를 순서대로 읽어 `cellCounts`를 집계한다. 정수 덧셈을 고정 순서로 하므로 스레드 스케줄링에 결과가 흔들리지 않는다.
3. `_positions`, `_velocities`는 `Allocator.Persistent`.
4. `OnDisable`과 `OnDestroy`에서 `_handle.Complete()` 후 `IsCreated`를 확인하고 해제한다.
5. `UnityEngine.Random.InitState(seed)`로 원본 분포를 유지하고, 전역 난수 상태는 백업·복구한다.
6. `unsafe`와 `NativeDisableParallelForRestriction`은 쓰지 않는다.

**두 후보에서 고를 때의 판단 (내 의견이고 미검증)**

| 결정 지점 | 권장 | 이유 |
|---|---|---|
| `Random` 표기 | `UnityEngine.Random`으로 완전 한정 | `using UnityEngine`과 `using Unity.Mathematics`가 둘 다 있으면 모호 참조 가능성 |
| `MoveJob` 의존성 | 인덱스 계산 Job에만 의존 (GPT 구성) | 합산과 병렬 실행 가능. 결과는 같음 |
| `Update()`의 `Complete()` | 유지해도 해 없음 | 필수는 아님. 두 모델이 입장을 바꿨지만 둘 다 해가 없다고 봄 |
| `count <= 0` 가드 | 채택 | 두 모델 모두 채택, 비용 거의 없음 |
| 비유한(NaN) 좌표 처리 | **보류** | 지금은 속도가 0이라 생길 경로가 없음. 속도 사양이 정해질 때 함께 결정 |
| 카운터 `int` vs `long` | **사용자 결정** | 프레임별 집계(최대 20000)엔 `int`로 충분. 누적이면 오버플로 정책 필요 |
| 집계 모드 기본값 | **사용자 결정** | 임의 기본값(Gemini) vs 선택 강제(GPT `Unspecified`) |
| 합산 Job의 직렬 구간 | 측정 후 판단 | 20000개 규모의 비용은 미측정 |

두 후보를 합친 코드는 아직 안 만들었어. 필요하면 위 표대로 합친 버전을 만들어줄게. 그 코드도 컴파일은 안 한 상태야.

## 5. 미해결 위험과 사용자 질문

**사양 결정 대기 (사용자)**

| 질문 | 현재 처리 |
|---|---|
| `cellCounts`를 매 프레임 새로 셀지, 누적할지 | 두 경우 조건부. 모드 스위치로 대응 |
| 속도 0이 의도인지, 이동이 필요한지 (필요하면 카운팅 시점이 이동 전/후 중 어느 쪽인지도) | 원본대로 0 유지 |
| 셀 수식 `abs(x) % 1024`가 의도인지 (현재 0~50번 셀만 사용, 음수·양수 좌표가 같은 셀) | 수식 유지, 임의 수정 안 함 |
| 비유한 좌표를 제외할지, 별도 카운트할지 | 보류 |
| 누적 모드의 카운터 타입 | 보류 |

**범위 밖으로 남긴 것**: (b) 프레임 레이트 독립성, (c) 플랫폼 간 비트 동일성. 속도가 채워지는 시점에 다시 검토.

**실행 검증 대기**: S2-09(예외 타입·위치), S2-10(`TempJob` 경고와 씬 종료 에러의 관계), S2-22(`Random` 모호 참조), S2-13·S2-24(성능과 직렬 합산 비용), 에디터와 빌드의 초기 위치 일치(S2-15).

## 6. 실행 계획과 검증 기준 (Phase 5)

두 모델의 테스트 계획을 합쳤어. Gemini에는 있고 GPT에는 없던 "원본 실행" 항목이 이 샘플의 핵심 미해결(S2-09)이라 가장 앞에 뒀어.

| 순서 | 테스트 | 통과 기준 |
|---|---|---|
| 1 | **원본 코드를 에디터에서 그대로 실행** (안전성 검사 켬) | 예외 메시지 전문과 스택 트레이스 첫 줄, 발생 빈도, `JobTempAlloc` 경고, 씬 종료 에러를 각각 기록 |
| 2 | **원인 분리 실험**: 원본에서 ⒜ 생명주기만 수정, ⒝ 쓰기 경쟁만 수정, ⒞ 시드+초기화만 수정 | 어느 변경이 어느 증상을 없애는지 표로 기록 (증상 ①의 원인 확정용) |
| 3 | 원본을 빌드에서 실행 (시드 고정+프레임마다 초기화만 한 상태) | `cell0`이 실행마다 흔들리면 경쟁이 증상 ②의 원인으로 확인 |
| 4 | `unsafe` 비활성 상태로 수정 코드 컴파일 | 오류 0건 (모호 참조 포함) |
| 5 | 모든 x를 0으로 고정, 전체 1024개 셀 비교 | 프레임별: `cellCounts[0] == 20000`, 합 == 20000. 누적: t번째 틱에 20000×t |
| 6 | 같은 시드·같은 틱 수로 에디터 3회, 빌드 3회 | **전체 `cellCounts` 배열**이 모든 실행에서 동일 (`cell0`만 비교하지 않음) |
| 7 | 에디터와 빌드의 초기 위치 배열 비교 | 동일 시드에서 일치 (일치하지 않으면 시드 방식 재검토) |
| 8 | Job 예약 직후 비활성화·파괴, 씬 반복 로드·언로드 | 예외와 경고 0건 |
| 9 | `count = 0 / -1`, 모드 미선택 | 안전하게 중단 |
| 10 | 성능 프로파일 (Burst, `Debug.Log` 제외, 균등/단일 셀 집중) | 직렬 합산 구간의 실측 시간 기록 |
| 11 | (비유한 정책을 채택한 경우) `NaN`, ±∞ 입력 | 인덱스 오류 없이 정책대로 처리 |

**재심 조건**: 2번에서 증상 ①의 원인이 생명주기로 나오면 Gemini P2의 추론이, 인덱스 위반으로 나오면 GPT 입장이 맞았던 것으로 장부를 갱신하고 해당 부분을 재검토해.

## 7. 실험 지표 (명세서 8장)

| 항목 | 기록 |
|---|---|
| 합의된 핵심 결함 | 6개 (경쟁, TempJob, Dispose 전 Complete 누락, 시드, 누적·초기화, 속도 0) 모두 양쪽이 발견 |

**해석 한계**
- 두 샘플 모두 결함을 심은 코드이고, 나는 정답을 아는 상태에서 판정했어. 판정 근거는 코드 논리와 문서 수준이라 Phase 5 전에는 확정이 아니야.
- GPT만 검색을 썼을 가능성이 있고, 응답 시간은 모드와 검색 조건이 같은지 확인이 안 돼서 모델 우열의 근거로 쓰지 않아.
- Gemini의 대화가 매번 새 대화였는지는 사용자 확인에 의존했어.

## 8. 두 샘플에서 보인 경향 (n=2, 잠정)

- 핵심 결함은 모델 조합과 무관하게 둘 다 찾았고, **차이는 가장자리에서 났어.** 샘플 2에서는 셀 범위 누락(Gemini)과 컴파일 위험(Gemini)이었고, 샘플 1에서는 stale 결과 덮어쓰기 등이었어.
- 교차 검토는 과장된 주장(성능 수치, 예외 타입 단정)을 걸러내는 데 효과가 있었어.
- 모델이 상대 결과를 읽고 **입장을 상대 쪽으로 옮기는 현상**이 보였어(S2-09). 합의가 증거가 아니라는 규칙이 실제로 필요했던 사례야.
- 모델이 보고한 수치(줄 수, 상태 수)는 4번 중 3번 틀렸어. 자동화 때는 측정값을 코드로 계산해서 쓰는 게 안전해.
- 이번 실험의 오류는 대부분 수동 전달 과정(잘못된 첨부, 재작성본, 오염된 대화)에서 나왔어. API 호출로 자동화하면 줄어들 부분이야.

## 샘플 2: BoidSystem (디버깅)

### 사양 확정 상태 (지휘자에게 답한 내용)

| 질문 | 답변 |
|---|---|
| `cellCounts` 초기화/누적 | 미정 (사용자도 모름) |
| `_velocities` 0, 셀 수식 | 미정 (사용자도 모름) |
| `unsafe` | 비허용 |
| 스택 트레이스 | 없음 (Phase 5에서 확보) |
| "결정적"의 의미 | (a) 같은 시드, 같은 틱 수에서 같은 결과. 스레드 경쟁으로 결과가 흔들리지 않는 것이 핵심 |

### 확정 결함 (사양과 무관하므로 조건부로 흐리면 감점)

| ID | 결함 | 심각도 | 발생 조건 / 비고 |
|---|---|---|---|
| B-01 | `CountJob`의 `cellCounts[cell]++`가 인덱스 `i`가 아닌 위치에 병렬로 쓰는 경쟁 상태 | 높음 | 에디터(Safety System)에서는 병렬 쓰기 범위 제한 위반으로 InvalidOperationException. 빌드에서는 예외 없이 카운트 유실. 증상 1, 2번과 일치 |
| B-02 | `OnDestroy`에서 `_handle.Complete()` 없이 Dispose | 높음 | 증상 3번. Update와 LateUpdate 사이에 비활성화되거나 파괴되어 잡이 미완료일 때, 또는 종료 시점에 간헐적으로 발생 |
| B-03 | `Allocator.TempJob`을 `Start`에서 할당해 객체 수명 동안 보유 | 중간 | TempJob은 4프레임 내 해제 계약이라 경고 발생. `Persistent` 사용해야 함 |
| B-07 | `LateUpdate`의 `Debug.Log` 문자열 보간으로 매 프레임 GC 할당 | 낮음 | 사양과 무관한 확정 결함이지만 중요도는 낮음 |

### 규칙 E 테스트 항목 (사양 미정이라 조건부 처리가 정답)

| ID | 결함 | 심각도 | 올바른 처리 |
|---|---|---|---|
| B-04 | `_cellCounts`를 프레임마다 초기화하지 않아 누적됨 | 중간 | "프레임별 집계가 의도라면 결함, 누적이 의도라면 오버플로 위험만 존재"처럼 양쪽 조건부로 쓰거나 질문으로 남기기. **"명백한 버그"로 단정하면 감점** |
| B-05 | `abs(x) % 1024`는 x 범위가 ±50이라 약 51개 셀만 사용됨 | 낮음 | 임시 코드인지 의도된 사양인지 확인 질문. 단정하거나 "임시니까 무시"하면 감점 |
| B-06 | `_velocities`를 채우는 코드가 없어 개체가 움직이지 않음 | 낮음 | 위와 동일 |

### 함정 수정안

`[NativeDisableParallelForRestriction]`을 붙이는 수정안은 에디터 예외만 사라지고 경쟁 상태(B-01)는 그대로라서 증상만 숨기는 수정이야. 모델이 이걸 "해결책"으로 제시하면 **수정 품질 감점**으로 기록해.

올바른 방향은 `unsafe` 없는 병렬 안전 구조야.
- 배치/스레드별 로컬 카운트 후 병합 (2단계 잡)
- `NativeStream`, `NativeQueue.ParallelWriter` 등 병렬 안전 구조
- 이 쪽이 `unsafe` 비허용 제약과도 맞음. `Interlocked` 계열을 `unsafe` 포인터로 쓰는 수정안이 나오면 제약 위반으로 기록해.

### 오탐 유도용 (결함 아님)
- `_cellCounts`만 `Persistent`인 것은 정상
- `h1` 의존성 체인은 두 잡이 모두 `_positions`에 접근하므로 필요함
- `Start`에서 `UnityEngine.Random`을 메인 스레드로 쓰는 것은 정상
- 첫 프레임에 `default(JobHandle).Complete()`를 호출하는 것은 안전
- `Time.deltaTime`을 잡 생성 시점에 복사해 넘기는 것은 올바른 패턴

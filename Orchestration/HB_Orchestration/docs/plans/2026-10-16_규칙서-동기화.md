# 규칙서 동기화 — REVIEW_GUIDELINES 통일, 동기화 스크립트, docs/plans LF 고정

## 요약

- `REVIEW_GUIDELINES.md`의 Unity 쪽에만 있는 "Unity 공식 문서 참조" 절을 원본(`project-files/`)에 합치고 Unity로 복사한다.
- `project-files/` → Unity 프로젝트 동기화 스크립트를 추가한다. 기본은 비교만 하고, 적용하면 복사한 뒤 해시를 비교한다. Unity 쪽에서 고친 파일은 덮지 않고 멈춘다.
- `.gitattributes`에 `docs/plans/` LF 고정을 추가한다.

## 계획

### 1. REVIEW_GUIDELINES.md 통일

1. Unity 쪽 파일의 `## Unity 공식 문서 참조` 절(35~46줄)을 원본 끝에 붙인다. 내용은 바이트 그대로 옮긴다 (명령으로 추출해서 붙이고, 손으로 다시 쓰지 않는다).
2. 원본과 Unity 쪽이 같아지는지 해시로 확인한다. 2의 스크립트가 있으면 그것으로 복사·확인한다 (순서: 2 → 1).
   - 이 절은 Unity 쪽 내용을 원본에 합치는 것이다. 합친 뒤에는 Unity 파일 = 원본이 되어야 하므로, 복사하기 전에도 해시가 같아야 한다.
3. README 5절 원본 방향 문구를 `CLAUDE.md` 한 파일에서 "`project-files/`의 동기화 대상 전체"로 넓힌다.

### 2. 동기화 스크립트

**파일:** `Orchestration/HB_Orchestration/tools/Sync-ProjectFiles.ps1` (Windows PowerShell 5.1에서 동작, 외부 의존 없음)

**사용법**
```
powershell -File tools/Sync-ProjectFiles.ps1 -UnityProject F:\AI\ToolCreate          # 비교만 (기본)
powershell -File tools/Sync-ProjectFiles.ps1 -UnityProject F:\AI\ToolCreate -Apply   # 복사 + 해시 확인
```

**파일 구분**

| 구분 | 파일 | 동작 |
|---|---|---|
| 동기화 | `CLAUDE.md`, `REVIEW_GUIDELINES.md`, `.claude/commands/*.md` | 원본과 바이트 동일해야 함. `-Apply`면 복사 |
| 확인만 | `.claude/settings.json` | README에 "기존 파일이 있으면 `allow` 항목만 합치기"로 돼 있다. 덮지 않고 같음/다름만 표시 |
| 제외 | `.mcp.json` | 기기마다 경로가 다른 템플릿이다. 표시하지 않는다 |

목록은 스크립트 안에 고정한다. `.claude/commands/*.md`는 원본 폴더의 파일을 세서 정하고, Unity 쪽에만 있는 명령 파일은 "Unity에만 있음"으로 표시만 한다 (지우지 않음).

**출력:** 파일마다 한 줄 `상태  경로  원본해시  Unity해시`. 상태는 `같음` / `다름` / `Unity에 없음` / `Unity에만 있음` / `확인만-다름`. 끝에 요약 한 줄. 종료 코드 `0` = 동기화 대상이 모두 같음, `1` = 다른 것이 있음, `2` = 실행 오류(경로 없음 등).

**`-Apply` 규칙**
1. 먼저 비교한다.
2. **다름이 있으면 덮지 않고 멈춘다** (종료 코드 1). 그 파일 목록과 "`-Force`로 덮거나 원본에 먼저 합치세요"라는 안내를 출력한다.
   - 이유: 세 번 모두 Unity 쪽에서 직접 고친 내용이 있었다. 무조건 덮으면 그 내용이 사라진다. 이번 `cross-review.md` 1번 항목이 그 예다.
   - `Unity에 없음`인 파일은 덮을 것이 없으니 바로 복사한다.
3. `-Force`면 다른 파일도 복사한다. 덮기 전에 Unity 쪽 파일을 `<Unity>/review_tmp/sync-backup/<yyyyMMdd-HHmmss>/`에 백업한다 (`review_tmp/`는 이미 Unity `.gitignore`에 있다).
4. 복사는 `Copy-Item`(바이트 그대로). 복사한 뒤 모든 동기화 대상을 다시 해시 비교하고, 하나라도 다르면 종료 코드 1.

**README:** 5절 "복사" 설명을 스크립트 사용법으로 바꾼다. 손으로 복사하는 방법은 쓰지 않는다.

### 3. .gitattributes

`Orchestration/HB_Orchestration/.gitattributes`에 추가:
```
# 계획서. 사용자 답을 바이트 그대로 인용하므로 줄바꿈을 LF로 고정한다.
docs/plans/** text eol=lf
```
지금 파일이 이미 `i/lf w/lf`라 다시 정규화할 것은 없다. `git ls-files --eol`과 `git check-attr`로 확인만 한다.

### 순서

3 → 2 → 1 → `cross-review.md` (사용자 답에 따라) → README → 작업 로그 (`ch4_worklog.md`)

## 버린 대안과 이유

| 대안 | 버린 이유 |
|---|---|
| `HB_Orchestration.bat` 메뉴에 동기화 추가 | 배치 파일은 publish·대시보드 전용이고, 해시 비교·백업을 cmd로 쓰면 길고 테스트하기 어렵다. 스크립트를 먼저 두고, 메뉴에서 부를지는 나중에 정한다 |
| Unity 쪽 파일을 링크(심볼릭·junction)로 연결 | 복사가 필요 없어지지만 Unity 저장소에 다른 저장소를 가리키는 링크가 생긴다. 다른 PC나 git에서 깨지고, Claude Code의 `@` 불러오기가 링크를 따라가는지도 확인되지 않았다 |
| `-Apply`가 무조건 덮기 | 위 2-2의 이유. Unity 쪽 수정이 소리 없이 사라진다 |
| 동기화 대상 목록을 설정 파일로 | 파일이 6개뿐이라 스크립트 안에 고정하는 편이 단순하다. 늘어나면 바꾼다 |
| Unity → 원본 방향 자동 병합 | 원본 방향 원칙(원본을 고친 뒤 복사)과 반대다. 다른 파일이 나오면 사람이 보고 원본에 합친다 |

## 위험

- **`-Force` 백업 위치:** `review_tmp/`는 리뷰 사본용 폴더라 용도가 섞인다. 다만 이미 `.gitignore`에 있고, 백업은 지우지 않는 한 남는다.
- **`project-files/` 나머지 파일의 줄바꿈:** 이번 3은 `docs/plans/`만 고정한다. `REVIEW_GUIDELINES.md`와 명령 파일은 속성이 없어, 다시 체크아웃하면 CRLF가 되고 Unity 쪽(LF)과 해시가 달라질 수 있다. 스크립트는 그것을 `다름`으로 잡는다 (조용히 틀리지는 않는다). 근본 처리는 아래 질문 2.
- **Unity 공식 문서 절 중복:** 합치면 같은 절이 `CLAUDE.md`와 `REVIEW_GUIDELINES.md` 양쪽에 있다. `CLAUDE.md`가 `@REVIEW_GUIDELINES.md`로 불러오므로 지휘자 컨텍스트에는 두 번 들어간다 (약 12줄). 에이전트는 `REVIEW_GUIDELINES.md`만 받으므로 그쪽에는 필요하다. 아래 질문 3.
- **PowerShell 실행 정책:** `-File` 실행이 정책으로 막힐 수 있다. README에 `-ExecutionPolicy Bypass` 예시를 함께 적는다.

## 테스트

스크립트 테스트는 scratchpad의 임시 폴더 두 개(가짜 원본·가짜 Unity)로 한다. 실제 Unity 프로젝트에는 `-Apply`를 바로 쓰지 않는다.

| 경우 | 기대 |
|---|---|
| 모두 같음 | `같음`만, 종료 코드 0 |
| Unity에 없는 파일 | 비교: `Unity에 없음`, 1. `-Apply`: 복사 후 0 |
| 다른 파일 | 비교: `다름`, 1. `-Apply`: 복사하지 않음, 파일 그대로(해시 불변), 1 |
| 다른 파일 + `-Force` | 백업 폴더에 원래 Unity 파일(해시 일치), 복사 후 0 |
| `settings.json` 다름 | `확인만-다름`, `-Apply -Force`에도 덮지 않음 |
| `.mcp.json` 다름 | 출력에 없음, 종료 코드에 영향 없음 |
| Unity에만 있는 명령 파일 | `Unity에만 있음`, 지우지 않음 |
| 경로 없음 | 종료 코드 2 |
| 한글·CRLF 섞인 파일 | 복사 후 바이트 동일 |

## 실제 확인

1. 실제 Unity 프로젝트에 비교 모드 실행 → 지금 상태에서 `REVIEW_GUIDELINES.md`와 `cross-review.md`가 `다름`으로 나오는지 (스크립트가 실제 문제를 잡는지).
2. 1과 `cross-review.md`를 원본에서 처리한 뒤 `-Apply` → 종료 코드 0, 다시 비교해도 0.
3. `git ls-files --eol` / `git check-attr eol -- docs/plans/*`: `eol: lf`.
4. 다음 세션(규칙서는 세션 시작 때 읽힘): 세션 기록의 instructions 항목에 `REVIEW_GUIDELINES.md`가 있고 내용에 `## Unity 공식 문서 참조`가 있는지 (4장 마무리 3의 판정 기준). 스킬 목록의 `cross-review` 설명이 `\---`가 아닌지.

## 사용자에게 물을 것

1. **`cross-review.md`** — 이번 작업에 넣을까요? 넣는다면 원본의 1번 항목("대상 diff와 변경 의도를 파악한다 …")과 Unity 쪽 1번 항목("대상에 diff가 없으면 …")을 어떻게 할까요?
   - (가) Unity 쪽 문구로 바꾼다 (원본 1번 삭제)
   - (나) 둘 다 둔다 (원본 1번 다음에 Unity 문구를 새 항목으로)
   - (다) 이번에는 빼고 스크립트가 `다름`으로 보고하게만 둔다
2. **`project-files/` 나머지 줄바꿈** — 3에 `project-files/** text eol=lf`도 함께 넣을까요? (요청 범위는 `docs/plans/`만이라 묻습니다.)
3. **중복 절** — `CLAUDE.md`의 `## Unity 공식 문서 참조` 절을 그대로 둘까요, 아니면 `REVIEW_GUIDELINES.md`로 옮겨 지휘자 쪽 중복을 없앨까요? (요청은 합치기까지라, 기본은 그대로 둡니다.)
4. **커밋** — 끝나면 `ToolWithCS`에 커밋할까요? (Unity 쪽 파일은 미추적이라 커밋 대상이 없습니다.)

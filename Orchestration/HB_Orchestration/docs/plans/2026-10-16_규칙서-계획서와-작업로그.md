# 규칙서에 "계획서와 작업 로그" 절 추가

> 상태: **계획 — 승인 대기** (규칙서·문서 변경 없음)
> 작성: 2026-10-16
> 이 계획서의 위치(`docs/plans/`를 어느 저장소에 둘지)는 아래 "사용자에게 물을 것" 1번 결정에 따라 옮길 수 있다.

## 요약

- 규칙서 원본 `project-files/CLAUDE.md`의 `## 외부 에이전트` 절 다음에 `## 계획서와 작업 로그` 절을 새로 넣고, Unity `CLAUDE.md`에 복사한다. 두 파일의 SHA-256이 같은지 확인한다.
- 첫 적용으로 "4장 마무리 계획"을 계획서 파일로 남기고, 끝에 `## 결정` 절을 붙인다. 결정 절에는 사용자 답 (가)·(나)를 원문 그대로 인용한다.
- 규칙 문구는 사용자가 준 그대로 넣는다. 다만 문구만으로는 정해지지 않는 세 가지(계획서 위치, 작업 로그 파일, 기존 `ch4_plan.md`)를 먼저 확인받는다.

## 배경

- 4장에서는 계획을 대화로 제시하고 승인을 받은 뒤 구현했다. 그런데 계획서가 파일로 남은 것은 처음 한 번(`docs/ch4_plan.md`, 사용자가 요청해서 작성)뿐이다.
- "4장 마무리 계획"은 대화에만 있고 파일이 없다. 사용자 답 (가)·(나)도 작업 로그에는 **요약**으로만 남았다 ("사용자 지시" 표기).
- 4장 작업 로그는 장 단위 파일(`docs/ch4_worklog.md`)이다. 장과 무관한 작업의 결과를 어디에 쓸지는 정해져 있지 않다.
- 규칙서는 4장 마무리에서 `project-files/CLAUDE.md`(원본) → Unity `CLAUDE.md`(복사본) 방향으로 정했다. 이번 변경도 원본을 고친 뒤 복사한다.

## 계획

### 1. 규칙서 절 추가

- **위치:** 원본 `project-files/CLAUDE.md`의 `## 외부 에이전트 (hb-orchestration MCP)` 절(하위 `###` 포함) 끝, `## Unity 테스트 (Unity CLI)` 바로 앞.
- **내용:** 사용자가 준 문구를 그대로 넣는다. 아래 "사용자에게 물을 것" 1·2번의 답에 따라 다음 두 곳만 문구를 정한다.
  - "1단계"의 `docs/plans/…` 앞에 저장소 기준을 밝힐지 (예: "작업 대상 저장소의 `docs/plans/…`")
  - "3단계"의 "작업 로그"가 어느 파일인지
- 서식은 기존 규칙서와 맞춘다 (`*` 목록, LF, 번호 목록 없음).
- Unity `CLAUDE.md`로 복사한 뒤 SHA-256 일치와 CR 0개를 확인한다.

### 2. 첫 적용: 4장 마무리 계획서

- `docs/plans/2026-10-16_4장-마무리.md`를 만든다.
  - **계획 본문:** 승인 전에 대화로 제시한 "4장 마무리 계획" 원문을 그대로 옮긴다.
  - 계획서 구성(요약 / 배경 / …)과는 형식이 다르다. 그래서 맨 위에 "대화로 제시한 계획을 사후에 파일로 옮김 — 본문은 당시 원문, 새 규칙의 구성과 다름"이라고 표시한다.
  - 내용을 새 구성에 맞춰 다시 쓰지 않는 이유: 그러면 승인 당시와 다른 문서가 된다.
- 끝에 `## 결정` 절을 덧붙인다.
  - 사용자 답 (가)·(나)를 **원문 그대로** 인용한다 (아래 "첫 적용 미리보기").
  - 그 답으로 바뀐 계획 항목을 따로 적는다.
- `docs/ch4_worklog.md`의 "4장 마무리" 절 첫 줄에 이 계획서 링크를 단다 (3단계 규칙).

### 3. 이 작업 자체의 기록

- **계획서:** 이 파일.
- **결정:** 승인을 받으면 이 파일 끝에 `## 결정` 절(사용자 답 원문 + 바뀐 항목)을 덧붙인다.
- **결과:** 작업 로그(위치는 "사용자에게 물을 것" 2번)에 절을 만들고, 첫 줄에 이 계획서 링크를 단다.
- **커밋:** 오케스트레이션 저장소에 1회. Unity `CLAUDE.md`는 Unity 저장소에서 미추적 파일이라 커밋 대상이 아니다.

## 첫 적용 미리보기 — 인용할 사용자 답 원문

대화 기록에서 "4장 마무리 계획"에 대한 사용자 답을 찾았다. 계획을 제시한 다음 메시지이고, 붙여넣기로 받은 텍스트다. 줄바꿈과 빈 줄을 포함해 받은 그대로다.

```text
(가) 계획대로 진행. 단, 다음을 반영:

등록 값 검사는 이번 호출에서 참조한 루트만. 잘못된 항목은 list_modes에 경고로만 표시하고, 다른 호출을 막지 않을 것.
@를 쓰지 않은 호출에서는 ContextRoots를 기록하지 않음(필드 생략). 테스트로 고정.
루트 이름의 대소문자 처리를 정하고 테스트 추가.
테스트 추가: 등록은 있으나 기존 경로만 쓰는 경우 바이트 동일 / 쓰지 않는 등록 항목이 깨져 있어도 정상 실행.
실제 확인 추가: 에이전트 입력에 로컬 절대 경로가 없는지 확인, 설정을 비운 뒤 list_modes 출력이 이전과 같은지 확인.

(나) 문제 1·2를 고친 뒤 두 파일을 같은 내용으로. 번호는 1., 줄바꿈은 LF. 앞으로는 project-files/CLAUDE.md를 원본으로 하고 Unity 쪽은 복사본으로 둔다. 이 결정을 작업 로그와 README 5절에 남길 것.
```

**인용 방식:**
- 코드 블록(`text`)으로 넣는다. 인용(`>`)은 마크다운 렌더링 때 줄바꿈과 빈 줄이 합쳐지거나 `@`·`/` 같은 문자가 해석될 수 있다. 원문 그대로 보존하려고 코드 블록을 택했다.
- 결정 절의 "바뀐 계획 항목"은 인용과 분리해 내 문장으로 쓴다.

## 버린 대안과 이유

| 대안 | 버린 이유 |
|---|---|
| 규칙 문구를 내가 다듬어 넣기 | 사용자가 문구를 정해 줬다. 바꿀 필요가 있는 곳(위치·파일 지정)만 질문으로 올린다 |
| 4장 마무리 계획을 새 구성으로 다시 써서 계획서로 만들기 | 승인 당시 문서와 달라진다. "계획 본문은 고치지 않는다"는 새 규칙의 취지와도 맞지 않는다 |
| 사용자 답을 `>` 인용으로 넣기 | 렌더링에서 줄바꿈·빈 줄이 바뀔 수 있어 "원문 그대로"를 보장하지 못한다 |
| 4장 작업 로그의 기존 "사용자 지시" 요약을 원문으로 바꾸기 | 작업 로그의 지난 기록을 고치는 셈이다. 원문은 계획서의 결정 절에 두고, 작업 로그에서는 링크로 잇는다 |

## 테스트

코드 변경이 없어 자동 테스트는 없다. 다음을 확인한다.
- 원본과 복사본의 SHA-256 일치, 두 파일 모두 CR 0개
- 제목 구조: `## 외부 에이전트` → `## 계획서와 작업 로그` → `## Unity 테스트` 순서, 기존 절은 그대로 (추가 전후 diff가 새 절 추가뿐인지)
- 첫 적용 계획서: 결정 절 인용 블록의 내용이 위 원문과 바이트 단위로 같은지

사용자가 처음 준 문구와 실제로 규칙서에 넣는 문구의 차이는 아래 두 곳뿐이다. 나머지는 준 그대로다.

# 4장 마무리 계획

## 1. 허용 루트 추가 (`Context.ExtraRoots`)

### 설정 형식

```json
"Context": {
  "ExtraRoots": { "orch": "F:/AI/ToolWithCS/Orchestration/HB_Orchestration" }
}
```

- **이름 → 절대 경로**의 사전으로 둡니다. 기본은 빈 사전입니다.
- 이름 규칙은 영문·숫자·`_`·`-`, 2~32자입니다.
- appsettings는 호출마다 다시 읽히므로, 넣고 빼는 데 서버 재시작이 필요 없습니다.

### context에서 경로 지정: `@이름/상대경로`

```json
{ "path": "@orch/src/HB.Orchestration.Agents/SafePath.cs", "startLine": 1, "endLine": 80 }
```

`orch:src/…` 방식은 쓰지 않습니다. 기존 `path:line` 표기(`a.cs:12`, 기록의 `a.cs:1-80`)와 섞이고, Windows 드라이브 표기(`C:`)와도 헷갈리기 때문입니다. `ContextRange`에 `root` 필드를 새로 두는 방식도 쓰지 않습니다. 도구 스키마와 설명이 늘어나는데, 그 설명은 지휘자 컨텍스트에 늘 올라갑니다.

**ExtraRoots가 비었거나 등록되지 않은 이름이면 기존과 똑같이** 메인 루트 기준 상대 경로로 처리합니다. 예를 들어 `@orch/a.cs`는 메인 루트의 `@orch` 폴더로 해석되고, 보통은 "파일이 없습니다"로 끝납니다. 그래서 "비어 있으면 지금과 똑같이"가 보장됩니다.

다만 등록된 이름인데 경로가 잘못된 경우는 조용히 넘어가지 않고 오류로 돌려줍니다.

### 루트별 검사

- 등록된 루트 경로에는 기존 `SafePath.Resolve`를 그대로 적용합니다. 그 루트 밖, 절대 경로, 링크 경유, DenyPatterns 기준이 모두 같습니다. 전송 금지 목록(`.env`, `*.pem`, `.git/**` 등)도 그 루트 기준으로 적용됩니다.
- 등록 값 자체도 검사합니다. 절대 경로가 아니거나 폴더가 없으면 `[첨부 코드 오류] ExtraRoots 'orch': 폴더가 없습니다`처럼 실행 전에 거절합니다.
- 루트 자체가 junction인 경우는 지금처럼 허용합니다 (2-3 review R2와 같은 근거).

### 기록과 표시

- **에이전트에게 보내는 첨부 제목**은 `### @orch/src/…/SafePath.cs:1-80`입니다. 로컬 절대 경로는 외부로 보내지 않습니다.
- **`CallRecord.Context`**에도 같은 문자열 `@orch/src/…:1-80`이 남습니다.
- **`CallRecord.ContextRoots`**를 새로 추가합니다. 이번 호출에서 실제로 쓴 루트만 `{ "orch": "F:/…/HB_Orchestration" }` 형태로 남습니다. 나중에 설정을 비워도 그 기록이 어느 폴더에서 읽었는지 알 수 있고, 대시보드는 이 값으로 `@orch/…` 링크를 실제 파일 경로로 엽니다.
- **`list_modes` 마지막 줄**에 `추가 루트: @orch`를 표시합니다. 등록이 있을 때만 붙고, 경로는 빼고 이름만 보여 줍니다. 지휘자가 이름을 알아야 쓸 수 있기 때문이고, 비어 있으면 출력은 지금과 같습니다.

### 읽기만 적용 (사용자 의견과 같음)

`save_result`는 지금처럼 기록의 `ProjectDir` 하나에만 씁니다. `@이름/…` 경로를 주면 등록 여부와 상관없이 거절합니다: `[저장 불가] 추가 루트(@이름)에는 쓸 수 없습니다`.

이유:
- 쓰기는 다른 저장소의 파일을 바꿀 수 있어서, 읽기보다 실수했을 때의 피해가 큽니다.
- `save_result`의 목적은 "저장 위치를 그 세션의 프로젝트로 고정"하는 것입니다. 다른 루트에 쓸 수 있으면 3장의 저장 위치 이탈이 다시 가능해집니다.
- 거절 메시지를 명시적으로 두는 이유는, 메인 루트에 `@orch`라는 폴더를 실수로 만드는 일을 막기 위해서입니다.

### 테스트 (`ExtraRootsTests`)

| 경우 | 기대 |
|---|---|
| ExtraRoots 비어 있음 + 기존 경로 | 기존과 같은 첨부 텍스트·출처 문자열 (바이트 단위로 비교) |
| ExtraRoots 비어 있음 + `@x/a.cs` | 기존처럼 메인 루트 기준 → "파일이 없습니다" |
| 등록된 루트 안 정상 경로 | 성공, 제목과 출처가 `@orch/…:1-3`, 사용한 루트가 기록됨 |
| 등록된 루트 밖 (`@orch/../x.cs`) | "프로젝트 루트 밖입니다" |
| 등록된 루트 안 링크 경유 | 거절 (junction은 관리자 권한 없이 만들 수 있어 테스트에서 실제로 만듦) |
| 등록된 루트의 DenyPatterns (`@orch/.env`) | 거절 |
| 등록 값이 상대 경로이거나 없는 폴더 | 실행 전 오류 |
| save_result에 `@orch/…` | `[저장 불가]` |

### 실제 확인

1. 다시 publish합니다. 서버 종료가 필요해서 **그 시점에 다시 확인을 받겠습니다.**
2. 실제 설정에 `ExtraRoots: { "orch": "…/HB_Orchestration" }`을 넣습니다.
3. 오케스트레이션 저장소의 파일을 복사 없이 `@orch/…`로 넘겨 `review`를 1회 실행합니다.
4. calls.jsonl의 첨부 내용이 원본 파일의 해당 줄과 일치하는지, `ContextRoots` 기록이 남았는지 확인합니다.
5. 설정을 다시 비웁니다.

### Unity 프로젝트에만 해당하는 내용

`project-files/`는 README 5절대로 **Unity 프로젝트에 복사해 쓰는 템플릿**이라, "Unity 테스트"와 "Unity 공식 문서 참조" 절은 원래부터 양쪽에 다 있습니다. "이 Unity 프로젝트(ToolCreate)에만 해당"하는 내용은 다음 한 가지로 봤습니다.

| 위치 | 내용 | 제안 |
|---|---|---|
| "루트 밖 리뷰" 절 | `review_tmp/`가 `.gitignore`에 등록돼 있다는 전제. 이 프로젝트에만 방금 등록했습니다 | 배포용에는 "(프로젝트마다 `.gitignore`에 등록할 것)"을 덧붙임 |

### 기준 파일에서 발견한 문제 (고칠지 정해 주세요)

1. **절 위치:** "에이전트(모델) 교체"와 "프로젝트 루트 밖…" 두 절이 `## Unity 공식 문서 참조` 아래 `###`로 붙어 있습니다. 내용상 `## 외부 에이전트` 아래("결과 저장" 근처)가 맞습니다.
2. **이스케이프 잔재:** `` `run\\\_mode` ``, `` `list\\\_modes` ``, `` `\\\[...]` ``, `\\\\n`이 있습니다. 코드 스팬 안의 백슬래시는 그대로 보이므로, 렌더링하면 `run\\\_mode`처럼 나옵니다. 같은 파일의 새 절들은 `` `run_mode` ``로 바르게 쓰여 있습니다.

→ 제안: 두 파일 모두 1·2를 고친 뒤 같은 내용으로 맞춥니다. 고치지 말고 Unity 쪽을 그대로 복사하라고 하시면 그렇게 하겠습니다.

### 1번 이후 "루트 밖 리뷰" 절 개정안

```markdown
### 프로젝트 루트 밖의 코드를 리뷰할 때

* `context`는 기본적으로 이 세션을 연 폴더(프로젝트 루트) 안의 파일만 읽는다.
* 밖의 저장소가 서버 설정 `Context.ExtraRoots`에 등록돼 있으면 `@이름/상대경로`로 바로 넘긴다
  (예: `{"path": "@orch/src/Foo.cs", ...}`). 등록된 이름은 `list_modes` 마지막 줄 `추가 루트:`에 보인다.
  읽기 전용이다 — `save_result`는 추가 루트에 쓰지 않는다.
* 등록돼 있지 않으면 사용자에게 등록을 요청하거나, 그 저장소에서 세션을 다시 연다.
* ExtraRoots를 쓸 수 없을 때만 복사한다:
  * (기존 4개 항목 그대로) + 프로젝트마다 `review_tmp/`를 `.gitignore`에 등록
```
